# Estilo de ejecución (siempre activo)

- **⚡ MÁQUINA DE MEJORAS (Brandon 2026-07-17, DEFAULT)**: modo obsesivo de mejora continua — líder en proponer Y ejecutar. (1) En cada área tocada, buscá activamente la SIGUIENTE mejora (features, UX, estilos, datos, compliance); nunca cerrar en "quedó bien" sin la ronda siguiente propuesta o en marcha (compone con flujo autónomo: las obvias se aplican directo). (2) **Autocrítica adversarial ANTES de reportar**: releé tu propio diff como refutador — ¿qué rompí? ¿qué caso falta? ¿cómo se ve en dark/mobile? ¿qué diría un QA hostil? (3) **Obsesión ≠ volumen**: cada mejora con evidencia real (gates + navegador para UI/motion — lección LazyMotion `fc8de71f`: los gates estáticos no atrapan crashes de runtime); una mejora rota vale menos que ninguna. (4) UI siempre al estándar del DS (skill `bsm-design-system`) con screenshot light+dark (Playwright desbloqueado vía symlink chromium). (5) Cada patrón/gotcha nuevo → memoria, para que la máquina COMPONGA entre sesiones.
- **Effort por tier** (Fast-Path ADR-058): HOTFIX/bulk mecánico → modelo rápido (`haiku`/`sonnet` en subagentes); FEATURE → default; DANGER/INITIATIVE → `opus`/effort alto. No quemar xhigh en tareas mecánicas.
- **Generator ≠ evaluator**: lo que un agente construye lo verifica OTRO agente con contexto fresco (solo diff + criterios, solo gaps de correctness). Auto-elogio = anti-patrón.
- **Un fork hereda TODO tu contexto, incluida tu meta grande** (fricción real 2026-08-19): un fork despachado con una directiva angosta de sólo-lectura puede igual "ayudar" continuando la tarea grande de la conversación por su cuenta — llegó a stagear Y commitear código en paralelo mientras el hilo principal tocaba el mismo índice de git. Si el hilo principal va a seguir mutando el mismo estado (git index, un archivo) que el fork podría tocar: decile explícitamente "NO continúes ninguna otra tarea de la conversación, sólo esto" o esperá a terminar esa sección vos mismo antes de despachar. Para redirigir/parar un fork ya corriendo: `SendMessage(to: agentId)` o `TaskStop` — NUNCA `Agent(subagent_type:"fork")` de nuevo con el mismo `name` (crea un duplicado corriendo en simultáneo, no resume el original). Detalle completo en memoria `fork-tool-anomalous-response.md`.
- **Trust but verify**: hallazgos de auditores se verifican con evidencia directa (grep preciso, SELECT real, getComputedStyle) antes de actuar.
- **Context resets > compaction** en corridas largas: estado a archivos (SESSION_HANDOFF.md, tasks), sesión fresca retoma.
- **2 correcciones fallidas sobre lo mismo** → parar, replantear el prompt/approach, no insistir en loop.
- **Verificación PROACTIVA antes de "listo"** (A2): corré el gate (`tsc`/`lint`/`test`/`curl`/screenshot del área tocada) y pegá la evidencia en el MISMO mensaje, ANTES de afirmar hecho. El Stop hook agente es la red de seguridad, no el gate primario: si el hook tiene que bloquear, ya fallé. En tareas >1h o multi-paso, abrí con `/goal "<condición ejecutable>"` y dejá que el evaluador externo cierre.

- **Workflow-first en auditorías/migraciones** (C2): "auditá/migrá/revisá X" → workflow `audit-verificado` (verifier en contexto fresco + refutación adversarial) o fan-out con verify por hallazgo, NO N agentes sueltos sin verificación. Lo confirmó la investigación 2026: verifier independiente = la palanca #1 contra "alucinar terminado".
- **Podar > agregar** (meta): el harness ya está sobre-extendido. Antes de crear skill/hook/regla nueva, preguntá si una existente sirve o si hay que afilar/borrar. Menos superficie = mejor selección de tools (tool-search) y menos ruido de contexto.
- **Terminal robusto** (E, fricción real 2026-07-02): (1) `pkill`/`kill` devuelven exit≠0 sin match o al auto-matarse → en comandos compuestos SIEMPRE `pkill ... || true`, o mejor: llamadas separadas. Un `&&` después de pkill es un bug latente. (2) **Gate autoritativo de "listo"** para cambios con superficie server (pages/layouts/sitemap/libs de prerender) = `node scripts/build-gate.mjs` (mata dev→limpia .next→build→veredicto pegable→re-levanta dev; exit 0 = apto). `tsc --noEmit` NO atrapa errores de prerender ni el cache corrupto de `.next/dev`. (3) **RAM crítica** (mem-guard bloquea): los comandos livianos (free/ps/kill/pkill/cat/tail) pasan por allowlist — usalos para diagnosticar/liberar; recuperación: cerrar Playwright → `pkill -f next-server` → esperar 5s; NO correr tsc/build/curl pesado hasta ver >3GB libres. (4) `curl` a rutas dev frías compilan on-demand (10-60s) → warmear ANTES de verificar en browser; primer curl con `--max-time 120`.

- **Workflows vs session limit** (F1, fricción real 2026-07-13): un deep-research con 25 claims × 3 votos adversariales = 75+ agentes (~2M tokens) reventó el session limit a mitad del verify (los agentes fallan con "session limit", el workflow sigue y devuelve lo que alcanzó). En workflows grandes: verificar con votos SOLO claims de fuentes no-oficiales (changelog/docs oficiales = alta confianza, basta 1 fetch propio), cap de verify ~10 claims, y sintetizar inline si la síntesis murió — los datos quedan en journal.jsonl.
- **Velocidad de ejecución** (D): (1) typecheck rápido = **`tsgo --noEmit`** (Go nativo, ~53s, RAM liviana — corre junto al next-server de 8.5GB sin chocar) como PRE-CHECK; `tsc --noEmit` (incremental YA ON, no borrar `.tsbuildinfo`) = gate autoritativo final que matchea CI. OJO: tsgo (preview v7) es más estricto que tsc (ej. flagea `TS2869` que tsc no) → si tsgo marca algo, cruzá contra tsc antes de actuar. (2) **Gates lentos en background**: `tsc`/`test`/`build`/re-index → `run_in_background` y seguir; no bloquear esperando. (3) **Paralelismo por defecto**: N tool-calls/agentes independientes en 1 mensaje. (4) **Turnos <5min** para mantener el prompt cache caliente (TTL 5min). (5) **Warmup** `node scripts/warm-dev-routes.mjs` antes de verificar en browser (evita cold-compile Turbopack 9-16s→1.5s). (6) **RAM**: next-server come ~8.5GB; cerrar Playwright antes de `tsc` 8GB; preferir tsgo cuando hay procesos pesados vivos. (7) **lint pre-check = `npm run lint:fast`** (oxlint: 0.96s/117MB medido 2026-08-03 — era 7.6s con 506 hallazgos sin barrer; eslint 99s/1.8GB); `npm run lint` (eslint) sigue siendo el gate autoritativo (reglas custom design-tokens).
